# Acceptance host adapter

`scripts/acceptance/host.ts` implements the host protocol for [29](https://github.com/markdlabrecque/r2/issues/29). It is a library, not a command-line runner or an installed-service acceptance result. Tests use private temporary roots and synthetic command results. No service, original environment file, Tailscale configuration or production host was operated on.

## Coordinator interface

```ts
const host = new AcceptanceHost({
  root: syntheticRoot, execute: fakeCommands, clock: injectedClock,
  privileged: () => true, interactive: () => true,
  rootUid: syntheticUid, serviceUid: syntheticUid,
});
const facts = await host.inspect();
// Acquire AcceptanceRegistry's host/unit lease using facts.installation.
// Create/load the journal, reconcile recovery first, then prompt for each operation.
await host.operate(lease, 'disable-model', authority);
const recovery = await host.recover(lease, restoreAuthority);
```

Live wiring is deliberately not provided. `root`, ownership mappings, command execution and privilege/terminal callbacks are trusted adapter boundaries, not user-configurable CLI flags. A future live adapter must use `/`, root ownership, the verified installed `r2` UID, actual effective privilege and actual interactive terminal facts. Do not expose a root override or substitute the developer checkout for installed files. Never log raw adapter errors or command output.

Public exports:

- `AcceptanceHost.inspect(): Promise<HostFacts>` performs reads and fixed read-only commands. It returns installation binding, supported layout, service Node version, active/enabled status, restrictive permissions, generic health, loopback-only listener, listener state `loopback-only|absent|unsafe`, synchronized clock, private HTTPS and combined `ready`. Unknown formats and unsupported layouts throw a sanitized `HostError`. Inactive, disabled, unhealthy, extra-listener or unsynchronized installations cannot become mutation-ready. Inspection itself never starts a stopped installation.
- `operate(lease, operation, authority): Promise<void>` accepts only `restart`, `stop`, `start`, `disable-model`. It requires the same installation and an owned journal lease. `start` is only for this run's deliberate stop, not an initially stopped installation. Successful stop and model disable leave `cleanup.status = restore-needed`; neither is final acceptance evidence. A second normal host operation is blocked until recovery, except the matching `start` or `disable-model` after a deliberate stop. The latter loads the override before starting the owned stopped installation, for Case B. Pause-only API restoration debt does not prohibit otherwise-ready host operations, for Case C; restart/start preserve that debt and do not mark cleanup verified. These coordinator integrations are exercised with the actual host implementation in `tests/acceptance-runner.test.ts`.
- `recover(lease, authority): Promise<RecoveryResult>` uses a fresh `restore-model` approval. It reconciles existing host cleanup rather than replaying the interrupted operation. It returns `restore-needed`, `restored-and-verified`, `conflict` or `failed`, with a fixed instruction code. `hostRecoveryInstructions[code]` provides secret-free operator instructions. A verified no-op returns the journal's prior verified result without restarting again. Pause-only cleanup stays `restore-needed` for the API coordinator.
- `HostAuthority` requires literal `nonProduction: true`, `hostDisruption: true` and a `StageApproval` bound to the exact journal run, current stage and named operation. `outcome` must be `approved`. A consumed approval object cannot be reused in the same process, including across host instances. The coordinator must create approvals only from fresh interactive prompts, not deserialize them or copy an earlier affirmative response. These cooperating adapters are not a sandbox against malicious same-UID code.
- `HostError.code` is a bounded enum. Its message contains no raw causes, paths supplied by commands, stderr, credentials or config values. `RecoveryResult.instruction` is a fixed code, never an arbitrary error string.

The coordinator must check `pending` and cleanup before any new acceptance stage. Take over a stale lock through the same-run journal protocol before recovery after interruption. Never release a lock with unfinished cleanup. Export the journal reports after failures. A changed installed revision blocks automatic host operations, including recovery, and requires owner reconciliation.

## Supported installation and provenance

This adapter intentionally supports only the exact committed `deploy/r2.service` contents, installed as `/etc/systemd/system/r2.service`, with `/opt/r2`, `/etc/r2/r2.env`, `/var/lib/r2` and `/usr/bin/node`. It checks the installed unit hash and selected effective systemd properties. It accepts no unrelated drop-ins or extra EnvironmentFiles. Unit aliases, alternate executables, unknown show output, unsupported runtime versions and uncertain permissions block rather than being guessed.

The installed provenance file `/opt/r2/.r2-revision` must contain the full lowercase 40-hex reviewed installed commit, be root-owned, mode 0644 and not be linked. It is not inferred from this checkout or from an arbitrary build artifact. The current installation guide's `git archive` example does not create this file. Such an installation is blocked until the owner independently establishes truthful deployment provenance. This library neither provisions the file nor claims that a marker alone cryptographically attests the deployed tree.

`/etc/machine-id` supplies a bounded stable nonsecret identity that is hashed before returning it. Its supported file mode is 0644. The installed Node executable must be a regular root-owned 0755 file at `/usr/bin/node`. The active service's `/proc/<MainPID>/exe` must point there, and that executable, not `node` from shell PATH, must report Node 24. The sole loopback 3000 listener must report that same PID through `ss --processes`; hidden process details or a different PID block readiness. A deliberate start requires an absent listener and enabled service with a synchronized clock. Unsupported links/layouts block. The secret environment file is only stat'ed, never opened. Config directory/file modes are 0700/0600; data is owned by the installed service UID with mode 0700. Ancestors must be safe directories, not symlinks or group/world-writable paths. Root-owned sticky temporary ancestors are allowed for synthetic fixtures only along the tested paths.

The private Serve parser accepts a single HTTPS 443 endpoint under `*.ts.net`, a single `/` proxy to `http://127.0.0.1:3000`, and no enabled Funnel entries or unknown top-level fields. Unknown Tailscale/systemd versions may therefore block. This is not proof of tailnet ACLs, firewall policy, external access denial or browser TLS behavior. Those remain owner gates.

## Command adapter contract

`CommandExecutor` receives only fixed absolute executable names and fixed argument arrays. There is no shell, arbitrary command API, sudo password input, environment-file sourcing, deployment or credential operation. The separately scoped `reboot` method adds only fixed `systemctl reboot --no-ask-password`, behind the explicit preparation protocol. Requests specify a 10-second deadline, 16 KiB combined output bound, abort signal and a minimal environment with fixed `/usr/bin` PATH and C locale. Health uses unauthenticated loopback `/healthz`, a five-second curl bound and no proxies.

A future executor must spawn without a shell, replace rather than merge the request environment, enforce the output bound while streaming, kill the child on abort/overflow, and reap it before settling. The library checks result sizes too and bounds the caller's wait even if an injected executor violates cancellation. A timed-out mutation is never rolled back concurrently with its outstanding command. Recovery remains blocked for all host instances sharing that executor until it settles. A late result cannot clear the durable pending intent. Before normal mutation and before recovery touches files, the effective unit must report no pending systemd Job and a settled active/inactive/failed state. Killing a systemctl client does not cancel a systemd job. After process loss, the owner must establish that no old command remains before authorizing recovery. The journal's PID/boot/start checks establish runner identity, not the death of arbitrary orphan child processes. This limit matters for reboot integration.

## Model override and recovery order

The systemd runtime parent `/run/systemd/system` must already be a safe root-owned directory. After persisting drop-in ownership and reload intent, the library can create the shared `r2.service.d` container if absent. It validates an existing container without adopting or changing its permissions. The container is never treated as an owned file or removed, so empty directories may remain after cleanup or interruption. They do not alter systemd configuration. Recovery tolerates missing `/run` parents after reboot without recreating them.

1. Inspect supported layout, actual active service, runtime, permissions, clock, loopback listener and private Serve. Require all ready facts before disruptive normal operations. Verify there are no pre-existing artifact paths.
2. Persist operation intent, service restoration, daemon reload and both artifact fingerprints before side effects, through `JournalLease.beginMutation`. If that write throws, do nothing externally, even if the commit may have reached disk.
3. Exclusively create `/run/r2-acceptance-model.env` with mode 0600 and credential-free empty assignments for `OPENAI_API_KEY` and `OPENAI_MODEL`. A comment binds it to the run and intent UUID. Exclusively create `/run/systemd/system/r2.service.d/90-r2-acceptance.conf`, also mode 0600, appending that EnvironmentFile. File writes and parent directories are synced. Checkpoint each created artifact. Never overwrite or adopt an existing file, directory or symlink.
4. Daemon-reload, verify the effective EnvironmentFiles order is original file followed by the runner's override, and only then restart. `Environment=` alone is deliberately not used, because installed EnvironmentFile values win over it. Verify active status and generic health. Retain owned artifacts and restoration intent until explicit recovery.
5. On ordinary errors, reload the journal and attempt cleanup. Injected crash boundaries leave the pending intent for explicit recovery. A timeout retains failed cleanup and pending intent instead of racing a late command.
6. Recovery validates all owned artifacts before deleting any. Before deletion checkpoint `remove-intent`. Remove only regular, single-linked, correctly owned/mode files whose content fingerprint still matches. Missing files are reconciled as absent, not recreated. Sync parent directories and checkpoint each removal. Retain reload/service flags until all work is verified.
7. Daemon-reload when required, check effective supported unit configuration again, restore the originally active service, then verify active status and generic health. Only then clear host cleanup flags and resolve the exact pending intent. A still-needed API pause restore prevents `verified` cleanup. Repeated completed recovery performs no further mutations.

Changed files, symlinks, hard links, permission changes and changed unit identity block deletion. Unrelated drop-ins are never cleared. A partially written file does not match its intended fingerprint, so automatic cleanup deliberately stops with conflict. The owner must inspect and reconcile it privately using the fixed recovery instructions. Unknown external edits, uncertain journal writes, health failures and executor failures never produce a pass. Exclusive host ownership protects cooperating processes; it cannot defeat hostile root code swapping files between checks.

## Downstream responsibilities and evidence limits

The scenario coordinator must separately verify `/api/status` assistant-disabled and assistant-enabled facts. Host file writes and health are not evidence of model behavior, reminder delivery, provider acceptance or observed notification display. API pause restoration must be coordinated before releasing the host lease. No app data is deleted.

The reboot task must use its own separately approved preparation/resume protocol and actual boot/process facts. The reboot task adds `identity()` for stable installed binding, `bootId()` for bounded current boot reads, `inspectBoot()` for inspection plus a Running Tailscale backend, and `reboot(lease, authority)` for the fixed injected reboot command. The latter independently requires privilege, TTY, single-use run/stage/operation approval, supported ready installation, same boot, verified cleanup and an already-durable matching pending reboot intent. It is never called by regular inspection, service operations or coordinator continuation. See [acceptance-reboot.md](acceptance-reboot.md). Missing volatile files do not authorize recreation. Resume must acquire/take over the same host/unit lock, run host recovery with fresh approval, and preserve journal failures until verified. If the installed revision/layout changed, artifacts conflict, the old executor might still run, or the ownership gate is uncertain, stop for owner reconciliation.

`tests/acceptance-host.test.ts` exercises only synthetic behavior. Its effective environment evaluator uses a canary credential internally but never puts it into host facts, errors, journal or report. Passing tests do not establish real systemd behavior on an installed host, notification delivery, Firefox acceptance or Tailscale isolation.
